### **What is CAS**

CAS (Compare And Swap) is a hardware-level atomic operation widely used in concurrent programming.

The core idea is very simple:

```text
Compare:
    Is the current value equal to the expected value?

If Yes:
    Replace it with a new value.

If No:
    Do nothing.
```

This entire process is completed atomically by the CPU.

No thread can interrupt the operation halfway.

---

### **Why Do We Need CAS**

Consider a simple counter:

```java
private int count = 0;

public void increment() {
    count++;
}
```

The operation:

```java
count++;
```

is actually:

```text
1. Read count
2. Add 1
3. Write back
```

Suppose:

```text
count = 0
```

Thread A:

```text
Read count = 0
```

Thread B:

```text
Read count = 0
```

Thread A:

```text
Write count = 1
```

Thread B:

```text
Write count = 1
```

Final result:

```text
count = 1
```

Expected:

```text
count = 2
```

This is a race condition.

  

Traditionally we solve this using:

```java
synchronized
```

or

```java
ReentrantLock
```

However, locks involve:

- Context switching
- Blocking
- Thread scheduling
- Kernel participation (in some cases)

CAS provides a lock-free alternative.

---

### **CAS Workflow**

Assume:

```text
current value = 10
```

Thread A wants:

```text
10 → 11
```

CAS operation:

```text
CAS(10, 11)
```

Meaning:

```text
If current value == 10
    update to 11
Else
    fail
```

Result:

```text
10 == 10
```

Success.

  

Current value:

```text
11
```

---

Another thread:

```text
CAS(10, 12)
```

Current value:

```text
11
```

Comparison:

```text
11 != 10
```

CAS fails.

Nothing is updated.

---

### **CAS in Java**

The most common example:

```java
AtomicInteger
```

```java
AtomicInteger count = new AtomicInteger(0);

count.incrementAndGet();
```

Internally:

```java
for (;;) {
    int current = get();
    int next = current + 1;

    if (compareAndSet(current, next)) {
        return next;
    }
}
```

Equivalent logic:

```java
while (true) {

    int oldValue = current;

    int newValue = oldValue + 1;

    if (CAS(oldValue, newValue)) {
        break;
    }
}
```

If CAS fails:

```text
Retry
Retry
Retry
```

This is called a CAS Spin.

---

### **compareAndSet()**

Core API:

```java
boolean compareAndSet(
        int expectedValue,
        int newValue)
```

Example:

```java
AtomicInteger counter =
        new AtomicInteger(10);

boolean result =
        counter.compareAndSet(10, 20);
```

Result:

```text
counter = 20
result = true
```

If:

```java
counter.compareAndSet(10, 30);
```

Current value:

```text
20
```

Result:

```text
counter = 20
result = false
```

### **CAS and CPU Instructions**

CAS is not implemented by Java itself.

Eventually it relies on CPU atomic instructions.

Examples:

```text
CMPXCHG (x86)
LDXR/STXR (ARM)
```

Java calls:

```text
Unsafe
↓
JVM
↓
CPU Atomic Instruction
```

Therefore CAS is extremely fast.

### **CAS and Lock Implementation**

Many developers think:

```text
CAS replaces locks
```

This is not entirely correct.

  

In reality:

```text
Modern locks are built on CAS.
```

### **ReentrantLock and CAS**

ReentrantLock is based on:

```text
AQS (AbstractQueuedSynchronizer)
```

AQS contains:

```java
private volatile int state;
```

Lock acquisition:

```java
if (compareAndSetState(0, 1)) {
    owner = currentThread;
}
```

Meaning:

```text
state = 0
```

No thread owns the lock.

  

Thread A:

```text
CAS(0, 1)
```

Success.

Thread A acquires the lock.

---

Thread B:

```text
CAS(0, 1)
```

Current state:

```text
1
```

CAS fails.

Thread B enters the wait queue.

---

Workflow:

```text
Acquire Lock

CAS Success
      ↓
  Get Lock

CAS Fail
      ↓
 Enter AQS Queue
      ↓
    Park()
      ↓
 Wait Wakeup
```

---

### **Why ReentrantLock Is Faster Than synchronized**

Modern JDK versions have optimized both heavily.

However ReentrantLock gains flexibility because:

```text
1. CAS Fast Path
2. AQS Queue
3. Fair Lock Option
4. Interruptible Lock
5. Timeout Lock
```

The first attempt is usually:

```text
CAS
```

Only after contention becomes severe:

```text
Block
Queue
Park
```

This reduces expensive thread switching.

### **CAS in AQS**

AQS state transitions:

```text
Unlocked
state = 0
```

Acquire:

```text
CAS(0,1)
```

Success:

```text
state = 1
```

Release:

```text
state = 0
```

Wake next waiting thread.

  

Diagram:

```text
Thread A
     |
CAS(0,1)
     |
Success
     |
 Hold Lock
     |
Unlock
     |
state=0
     |
Wake Thread B
```

### **CAS Problems**

#### **1. ABA Problem**

Example:

```text
A → B → A
```

Thread 1:

```text
Read A
```

Thread 2:

```text
A → B → A
```

Thread 1:

```text
CAS(A, C)
```

Success.

  

However:

```text
The value changed before.
```

CAS cannot detect this.

  

Solution:

```java
AtomicStampedReference
```

Add version numbers:

```text
(A,1)
→
(B,2)
→
(A,3)
```

---

#### **2. Spin Cost**

CAS failure:

```text
Retry
Retry
Retry
Retry
```

CPU usage increases.

  

High contention:

```text
CAS becomes expensive.
```

Therefore locks still exist.

---

#### **3. Only Suitable for Simple State Updates**

Good:

```text
Counter
Flag
State Transition
```

Bad:

```text
Complex Business Logic
Multi-Step Transaction
```

In such cases:

```java
synchronized
```

or

```java
ReentrantLock
```

is usually easier.

|---|---|---|---|
|Blocking|No|Yes|Yes|
|Context Switch|No|Possible|Possible|
|Performance (Low Contention)|Highest|Good|Good|

|Fairness|No|No|Optional|
|Reentrant|No|Yes|Yes|
|Timeout|No|No|Yes|
|Interruptible|No|No|Yes|

### **Summary**

CAS (Compare And Swap) is a CPU-supported atomic operation that updates a value only when the current value matches an expected value.

Core logic:

```text
Expected Value
      ↓
Compare
      ↓
Match ?
   /    \
 Yes    No
  |      |
Update  Retry
```

In Java, CAS is the foundation of:

```text
AtomicXXX

AQS

ReentrantLock

ConcurrentHashMap

ThreadPoolExecutor
```

A very important understanding is:

```text
CAS is not an alternative to modern locks.

CAS is the foundation upon which modern locks are built.
```

Many concurrent frameworks first attempt:

```text
CAS Fast Path
```

and only when contention becomes high do they fall back to:

```text
Queue
Park
Wakeup
```

This combination of CAS + Queueing is exactly the core design idea behind AQS and ReentrantLock.
