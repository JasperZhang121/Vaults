# **NGINX — Linux Operations Cheat Sheet**

A practical reference for managing and troubleshooting NGINX on Linux servers.

## **1. Installation and Service Management**

### **Install NGINX**

**Ubuntu / Debian:**

```bash
sudo apt update
sudo apt install nginx
```

**RHEL / CentOS / Rocky Linux:**

```bash
sudo dnf install nginx
```

Older distributions may use `yum` instead of `dnf`.

### **Manage the NGINX service**

```bash
# Start NGINX
sudo systemctl start nginx

# Enable NGINX at boot
sudo systemctl enable nginx

# Check service status
systemctl status nginx

# Check whether NGINX is active
systemctl is-active nginx

# Reload configuration without a full restart
sudo systemctl reload nginx

# Restart NGINX
sudo systemctl restart nginx

# Stop NGINX
sudo systemctl stop nginx
```

**Production tip:** Prefer `reload` over `restart` when applying configuration changes. A successful reload allows existing connections to be handled gracefully.

## **2. Inspect NGINX Configuration**

### **Common configuration locations**

|**Path**|**Purpose**|
|---|---|
|`/etc/nginx/nginx.conf`|Main configuration file|
|`/etc/nginx/conf.d/`|Additional configuration files|
|`/etc/nginx/sites-available/`|Site configurations, commonly on Ubuntu|
|`/etc/nginx/sites-enabled/`|Enabled site configurations, commonly on Ubuntu|
|`/var/log/nginx/`|Default log directory|

Actual paths depend on the distribution and deployment.

### **Essential commands**

```bash
# Check configuration syntax
sudo nginx -t

# Display the complete configuration, including included files
sudo nginx -T 2>&1 | less

# Find a specific domain
sudo nginx -T 2>&1 | grep -nC 5 'api.example.com'

# Find upstream definitions
sudo nginx -T 2>&1 | grep -n 'upstream'

# Find proxy destinations
sudo nginx -T 2>&1 | grep -n 'proxy_pass'

# Find header forwarding configurations
sudo nginx -T 2>&1 | grep -n 'proxy_set_header'
```

`nginx -T` is particularly useful when configuration is distributed across multiple files.

**Important:** It displays configuration files currently on disk, which may differ from the configuration last successfully loaded by the running NGINX process.

---

## **3. Apply Configuration Changes Safely**

After modifying an NGINX configuration:

```bash
# Validate the configuration
sudo nginx -t

# Reload only if validation succeeds
sudo nginx -t && sudo systemctl reload nginx

# Confirm the service is running
systemctl status nginx
```

For production changes, review the configuration diff and have a rollback plan before reloading.

A successful syntax check does not guarantee that upstream services are reachable or that routing behaves as intended.

## **4. Check Processes, Ports, and Connectivity**

```bash
# Display NGINX processes
ps -ef | grep '[n]ginx'

# Check listening ports
sudo ss -lntp | grep nginx

# Test the local HTTP endpoint
curl -I http://127.0.0.1

# Display response headers and status
curl -i http://127.0.0.1/health

# Test a specific virtual host against a local NGINX instance
curl -i -H 'Host: api.example.com' http://127.0.0.1/health

# Test an HTTPS virtual host against a specific IP
curl -i --resolve api.example.com:443:10.0.0.10 \
  https://api.example.com/health
```

The last command is useful for testing a specific NGINX server while preserving the intended HTTPS hostname.

## **5. Inspect Access and Error Logs**

Typical log files:

```text
/var/log/nginx/access.log
/var/log/nginx/error.log
```

### **View recent logs**

```bash
# Last 100 access log entries
tail -n 100 /var/log/nginx/access.log

# Last 100 error log entries
tail -n 100 /var/log/nginx/error.log

# Follow incoming requests
tail -f /var/log/nginx/access.log

# Follow errors in real time
tail -f /var/log/nginx/error.log
```

### **Browse large log files**

```bash
less -S +G /var/log/nginx/access.log
```

Useful shortcuts inside `less`:

|**Shortcut**|**Action**|
|---|---|
|`G`|Go to the end|
|`g`|Go to the beginning|
|`/keyword`|Search forward|
|`?keyword`|Search backward|
|`n`|Next match|
|`N`|Previous match|
|`F`|Follow new log entries|
|`Ctrl+C`|Stop following|
|`q`|Quit|

`less` is especially convenient when you need to search, scroll, and inspect surrounding log entries interactively.

## **6. Search Logs Efficiently**

### **Find requests and errors**

```bash
# Search for an API endpoint
grep '/api/orders' /var/log/nginx/access.log

# Search for a request ID
grep 'abc123' /var/log/nginx/access.log

# Display line numbers and surrounding entries
grep -nC 5 'abc123' /var/log/nginx/access.log

# Filter requests by endpoint and HTTP status
grep '/api/orders' /var/log/nginx/access.log | grep '" 502 '

# Count matching entries
grep -c '/api/orders' /var/log/nginx/access.log

# Search and browse results
grep '/api/orders' /var/log/nginx/access.log | less -S
```

Status-code searches depend on the configured access log format.

### **Search by date**

```bash
# Example for the standard NGINX date format
grep '24/Oct/2026' /var/log/nginx/access.log

# Search compressed, rotated logs
zgrep '/api/orders' /var/log/nginx/access.log*.gz
```

### **Common HTTP errors**

|**Status**|**Typical meaning**|
|---|---|
|`400`|Invalid client request|
|`403`|Access forbidden|
|`404`|Resource or route not found|
|`429`|Too many requests|
|`500`|Internal server error|
|`502`|Invalid or unsuccessful response from upstream|
|`503`|Service unavailable|
|`504`|Upstream response timeout|

These are starting points for investigation, not definitive diagnoses.

**Production tip:** A request ID shared across NGINX, Ingress, and application logs makes tracing individual requests much easier.

## **7. Inspect System Logs**

NGINX startup failures and service management errors may appear in the system journal.

```bash
# Recent NGINX service logs
sudo journalctl -u nginx -n 100 --no-pager

# Follow service logs
sudo journalctl -u nginx -f

# Logs since today
sudo journalctl -u nginx --since today

# Logs from the last hour
sudo journalctl -u nginx --since "1 hour ago"
```

Use `journalctl` alongside `error.log` when investigating startup or reload failures.

## **8. Understand Request Routing**

In a typical microservice architecture:

```text
Client
  |
  v
NGINX
  |-- Host: dev.example.com
  |-- Host: test.example.com
  |-- Host: prod.example.com
  |
  v
Location / API Route
  |
  v
Upstream / Ingress / Kubernetes Service
  |
  v
Application Pods
```

Key configuration directives:

|**Directive**|**Purpose**|
|---|---|
|`listen`|Listening port and address|
|`server_name`|Virtual host matching|
|`location`|URI-based routing|
|`proxy_pass`|Forward requests to an upstream|
|`upstream`|Define backend server groups|
|`proxy_set_header`|Set or override forwarded request headers|
|`proxy_connect_timeout`|Upstream connection timeout|
|`proxy_read_timeout`|Timeout between upstream response reads|
|`client_max_body_size`|Maximum allowed request body size|
|`access_log`|Access log configuration|
|`error_log`|Error log configuration|

### **Shared proxy headers**

Common proxy headers can be configured at the `http` level:

```nginx
http {
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Request-ID $request_id;

    # Server and upstream configurations...
}
```

These settings are inherited by lower configuration levels unless overridden.

**Important:** Defining any `proxy_set_header` at a lower level prevents inheritance of the entire parent set. Review existing configurations before relying on shared headers.

The IP-forwarding example assumes NGINX receives requests directly from clients. If other trusted proxies are involved, configure client IP handling accordingly.

Ordinary incoming headers, such as `Authorization`, are generally forwarded automatically unless explicitly modified.

## **9. Quick Production Troubleshooting**

When investigating an NGINX-related issue, follow a simple sequence.

**Step 1 — Check service health**

```bash
systemctl status nginx
sudo nginx -t
```

**Step 2 — Identify the active routing configuration**

```bash
sudo nginx -T 2>&1 | less
```

Look for the relevant `server_name`, `location`, and `proxy_pass`.

**Step 3 — Find the affected request**

```bash
grep '/api/orders' /var/log/nginx/access.log | tail -n 30
```

**Step 4 — Inspect related errors**

```bash
tail -n 100 /var/log/nginx/error.log
```

**Step 5 — Check upstream connectivity**

```bash
curl -i http://10.0.0.10:8080/health
```

Use the actual upstream address and endpoint.

**Step 6 — Check system-level errors if necessary**

```bash
sudo journalctl -u nginx -n 100 --no-pager
```

If the request passes through an internal Ingress or Kubernetes Service, continue tracing it at that layer rather than assuming every failure originates in NGINX.

## **10. Essential Commands to Remember**

|**Task**|**Command**|
|---|---|
|Check service|`systemctl status nginx`|
|Validate configuration|`sudo nginx -t`|
|Inspect full configuration|`sudo nginx -T 2>&1 \| less`|
|Apply changes|`sudo nginx -t && sudo systemctl reload nginx`|
|Check listening ports|`sudo ss -lntp \| grep nginx`|
|View recent requests|`tail -n 100 /var/log/nginx/access.log`|
|Follow access logs|`tail -f /var/log/nginx/access.log`|
|Browse large logs|`less -S +G /var/log/nginx/access.log`|
|Search logs|`grep 'keyword' /var/log/nginx/access.log`|
|Search with context|`grep -nC 5 'keyword' /var/log/nginx/access.log`|
|Inspect errors|`tail -n 100 /var/log/nginx/error.log`|
|Inspect service logs|`sudo journalctl -u nginx -n 100 --no-pager`|

**Core principle:** Know how to inspect the running service, understand the effective routing configuration, locate relevant requests, and verify upstream connectivity before making changes.
